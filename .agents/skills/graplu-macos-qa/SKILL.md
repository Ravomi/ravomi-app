# Ravomi macOS 测试工程师

交付可复现的测试结果、缺陷清单、性能数据和 GUI 改进建议。默认任务是测试与报告；修改产品源码、发布、向他人发送报告、配置定时任务不属于此技能的默认范围。

本技能仅安装于当前项目，目录和 `name: graplu-macos-qa` 保留兼容。Ravomi 是 Arcraven 的多 Agent 画布产品；按 [PRD](../../../PRD.md) 区分已实现基线与规划中的执行、编排和交接，不用静态 Agent 形象证明功能可用。

## 开始一轮测试

1. 确认目标 app、源码与报告目录。先查实际安装的 Ravomi；历史机器位置 `/Applications/Graplu.app`、`~/Projects/Graplu-codex-20261010` 仅用于旧安装定位，不假定它们存在或与当前源码一致。每轮在用户指定的报告目录建立独立时间目录，未指定时使用项目内 `results/macos-qa/<日期时间>/`；保留 `evidence/`、`logs/`、`metrics/`、`fixtures/` 和 `REPORT.md`，不要提交个人测试文档。
2. 阅读目标源码的 `AGENTS.md`、`PRD.md`、`DESIGN.md`、`AI_UI_RULES.md`、`DEVELOPMENT.md`、`VALIDATION.md`；明确本轮针对 Bevy、React/Tauri 或 Wry/React 哪个入口，不把未实现规划判为已实现功能的回归。记录 app 版本、可执行文件 SHA-256、源码版本（没有 Git 元数据则注明未知）、dirty 状态和本轮范围。不能假定本地源码与安装包相同。
3. 记录 macOS、芯片/内存、Metal 适配器、显示器物理分辨率/系统缩放/刷新率、窗口大小、UI 缩放、电源模式、前后台状态。缺失值写“未取得”。不要读取凭据或配置文件中的令牌。
4. 使用当前环境可用的窗口截图与控制工具；若使用 Hermes，则加载其 `computer-use` 技能。先后台操作，每次重要操作重新截图验证；工具返回成功不代表功能成功。Bevy 自绘画布可能没有 AX 子控件，依据新截图使用坐标。Hermes `coordinate` 的已知约定为截图左上角为原点的窗口相对像素；仍需核对当前工具文档，不要加 AXWindow 的桌面 x/y 偏移，也不要把 UI 逻辑单位或整屏坐标直接当截图坐标。先读实际截图尺寸并确认按钮中心；截图被缩放展示时按原图尺寸换算。切换窗口、调整尺寸或进入全屏后必须重抓截图并重新定位。无效果先检查坐标是否落在目标上；未命中不能算作应用不响应。`unverifiable` 仅表示工具未验证效果，应比较截图/状态。权限拒绝或正确定位后两次验证无效，记录 BLOCKED 并继续独立检查；不要绕过系统授权。
5. 使用测试副本、内置空白文档或自行创建的 fixtures，不覆盖用户原件。保留既有窗口；只关闭本轮自己创建且已记录的测试窗口/进程。不要修改全局 Hermes 人格、模型或网关配置。

## 执行顺序

先读 [测试矩阵](references/test-matrix.md)，选择冒烟、完整回归或专项范围。第一次至少完成冒烟、可行的性能基准和深浅主题检查。开始执行前在 REPORT.md 列出计划 case ID；每个用例使用 PASS / FAIL / BLOCKED / NOT_RUN / N/A，N/A 必须有适用性说明。

1. 安装包冒烟：启动、新建、中文编辑、保存副本、关闭重开、撤销重做。发现崩溃或数据丢失时先保留证据，再缩小复现；不继续破坏性操作。
2. 功能回归与 GUI 检查，记录步骤、期望、实际及证据。真实 IME、触控板、跨屏不能被文本注入、CLI 渲染或 headless 单测代替。
3. 如本轮包含源码验证，先串行完成项目要求的 fmt/test/clippy，保留命令、退出码和完整日志；纯安装包测试可以标 NOT_RUN。环境测试要核对字体、fixtures 和 macOS Metal 条件，不照搬 Linux Vulkan 命令。不为通过检查而改产品代码。
4. 编译与其它负载结束后再测性能。不要同时运行多个基准、录屏、构建或其它测试。无法获得空闲条件时明确记录干扰并降低结论可信度。
5. 按 [报告模板](references/report-template.md) 输出中文 REPORT.md。报告中的链接必须指向实际存在的工件；图片要实际查看，不能只列路径。最终答复提供报告路径、主要发现、覆盖率与阻塞项。

## 性能测量约定

优先使用安装包内的可执行文件。先核对目标源码参数解析；当前参数包括 `--benchmark`、`--synthetic N`、`--physics`、`--output PATH`、`--screenshot PATH`、`--light`、`--ui-scale N`、`--diagnostics`。当前入口在无文件参数时会自动加入 `--home`，即使指定 `--synthetic` 也会用首页盖住画布。画布基准须以测试 .prg 副本作为首个位置参数，随后加 `--synthetic N --benchmark --physics`，不要加 `--home`；先检查一次截图确实展示目标画布，再运行完整矩阵。没有 fixture 时先创建或取得已知测试文件，不能将首页遮挡场景充作正常画布基线。真实文档必须使用副本。不要假定 `--help` 是无副作用的帮助命令。

- 主基准使用 `--benchmark --physics` 保持产品推挤开启；关闭推挤只能作为另列的诊断对照。正式测量不加 `--diagnostics`，诊断模式单独运行并注明额外开销。
- 初始固定场景为 100、1000、5000 个合成节点，加一个已知复杂的 .prg 副本（无 fixture 则记 NOT_RUN）。每场景至少三次串行运行；保存各次 JSON、启动参数、日志与退出码。场景数减少时解释原因。
- 当前基准等待字形完成，再预热并测量静止/平移/缩放/拖动；从目标 `src/viewer.rs` 与 `src/stress.rs` 核对具体时长及采样语义。只有退出成功、JSON `valid:true`、四阶段非空且尺寸一致的数据可作有效样本。
- 按阶段展示 mean/p95/p99 帧间隔、样本数、每次结果及跨运行中位数/范围；不要平均各次 p95 伪称总体 p95。`1000 / mean_ms` 是吞吐估计，不是实际呈现 FPS。`load_ms` 不是完整启动时间，CPU 调度跨度不是纯 CPU 时间，帧间隔不是输入延迟。
- RSS、CPU 等缺失时写“未测”；确认 macOS 实现有效后才引用 JSON 的内存字段。需要额外采样时记录方法，区分瞬时值、均值、峰值和单位。
- 普通窗口的空闲资源与连续重绘基准分别测。60 Hz 的 16.67 ms / 120 Hz 的 8.33 ms 只作为帧预算参考；未批准的预算不称为产品发布门槛。首轮建立基线，不宣称已优化或跨机器加速。
- 和历史比较必须匹配二进制/场景/窗口/缩放/推挤/诊断配置，差异逐项列出。只有观测数据可支持性能结论；瓶颈假设另列验证方法。

## 缺陷与建议

严重度：S0 数据丢失或无法启动；S1 核心流程阻断；S2 功能错误或明显可用性问题；S3 局部视觉/文案问题。另给修复优先级 P0–P3，不把二者混用。每个缺陷包含最小复现、预期来源、实际结果、发生次数/尝试次数、证据与复测办法。

GUI 建议明确对应界面区域、用户影响、DESIGN.md / AI_UI_RULES.md 规则、具体调整方向和验收条件；复用共享主题/组件，旧基线与新规范的差距另列。验收素净层次、正文与连线清晰度、实际状态和人工介入入口；团子猫只保留一体轮廓、双耳双眼，石墨黑与雾蓝紫柔光不扩展到整个 UI。将“已验证缺陷”“待验证怀疑”“主观改进建议”分开。没有交互证据就不宣称按钮失效；没有对比度计算就不宣称数值达标；没有修改就不制作虚构的“优化后”截图。

结束条件：所选用例均有状态、数据有效性已审查、报告与原始证据落盘。未覆盖项不算通过；总体结果分“通过 / 不通过 / 验证不完整”，存在 S0/S1 或必测核心 FAIL 为不通过，核心 BLOCKED/NOT_RUN 为验证不完整。
